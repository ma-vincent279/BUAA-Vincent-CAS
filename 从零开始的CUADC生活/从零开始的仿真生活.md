## 一、为什么需要 SITL

**SITL = Software-In-The-Loop**：把**真实飞控固件**跑在电脑上，接一个**物理引擎**当"世界"。

```
真实飞行:   [机载程序] ──串口── [飞控固件] ──PWM── [电机] ──▶ 真实的空气与重力
仿真 SITL:  [机载程序] ──DDS──  [飞控固件] ──"PWM"── [物理引擎] ──▶ 模拟的空气与重力
                                        ↑ 同一份固件          ↑ Gazebo
```

**几个现实理由**：
- **省硬件**：不用真飞机就能跑 100 遍（我们跑了 11 轮 / 22 投来统计精度）
- **可复现**：同一份代码、同一个场地 seed ⇒ 结果可比较
- **能看到真相**：仿真里知道桶的**真实坐标**、飞机的**真实位姿** ⇒ 才能做误差归因
- **安全**：调参调崩了也不会摔飞机

⚠️ 但**仿真不是实机**：见 [`../技术全解.md`](../技术全解.md) 第三节 ——
**仿真分数不能代表真实精度**。

## 二、本项目用的仿真：PX4 SITL + Gazebo Harmonic

### 2.1 一次真实的迁移：Classic → Harmonic【源码事实】

| 时间 | 事件 |
|---|---|
| 项目早期 | 用 **Gazebo Classic**（`gazebo-classic_iris_mono_cam_down`）|
| **2026-10-12** | **整体迁到 Gazebo Harmonic (gz-sim8)** —— Classic 已停更、且物理精度和传感器模型更好 |
| 迁移后 | `SIM` 默认值也改成了 `gz`（**曾经因为没改默认值，`bash test_k.sh` 会走进已卸载的 Classic，而且要等 600 s 轮询才报错**）|

**迁移带来的一个坑（很重要）**：

```bash
sudo apt install ros-humble-ros-gzharmonic      # ✅ 必须这个
sudo apt install ros-humble-ros-gz              # ❌ 默认是 Fortress 变体, 与 Harmonic 不兼容
```

`ros-humble-ros-gz` 默认链接 `libignition-transport11`，
而 Harmonic 用 `gz-transport13` / `gz-msgs10` ⇒ **装错就桥不通** ✗

### 2.2 PX4 是怎么把 gz 拉起来的（讲透）【源码事实】

```
make px4_sitl_default ──► px4 二进制
    │
    └─ px4-rc.gzsim (启动脚本)
         ├─ 读 gz_env.sh  → 得到 PX4_GZ_WORLDS / PX4_GZ_MODELS / GZ_SIM_SERVER_CONFIG_PATH
         ├─ 启动 `gz sim` (Harmonic), 加载 **server.config** 里的 system plugin
         └─ 通过 gz-transport 把飞机模型 spawn 进世界
```

**三条硬规则（踩过才知道）**：

| 规则 | 违反的后果 |
|---|---|
| ① **世界文件里绝对不能声明 gz 的 system plugin** | 与 `server.config` 重复加载 ⇒ `Found 0 compass` / `barometer 0 missing` ⇒ **飞不了** ✗ |
| ② **世界文件必须有 `<spherical_coordinates>`** | GPS/磁罗盘算不出来 ⇒ `Preflight Fail: Strong magnetic interference` ✗ |
| ③ **世界文件名（不含扩展名）必须等于 `PX4_GZ_WORLD`** | 启动时 `Timed out waiting for Gazebo world` ✗ |

> 为什么是 ①：gz 的 system plugin 由 **`GZ_SIM_SERVER_CONFIG_PATH` 指向的 `server.config` 全局加载**
> （物理、IMU、气压计、磁罗盘、navsat、相机…），**不是**由世界文件加载的。
> 世界文件里再写一遍 = 加载两次 ⇒ 传感器冲突 ✓

**【源码事实】** 本项目为此打了一个**最小可回退**的补丁：
`~/PX4-Autopilot/src/modules/simulation/gz_bridge/gz_env.sh.in` 的 4 行
从 `export VAR=<固定值>` 改成 `export VAR="${VAR:-<固定值>}"`
⇒ **不设环境变量时行为完全一致**，但允许我们用**外部的模型/世界目录**覆盖 ✓
回退：`cd ~/PX4-Autopilot && git checkout -- src/modules/simulation/gz_bridge/gz_env.sh.in`

## 三、本项目的仿真三件套【源码事实】

| 件 | 文件 | 作用 |
|---|---|---|
| **① 场地生成器** | `scripts/gen_world_cuadc.py` | 一次生成 `.world` **和** `.truth.json` |
| **② 一键启动** | `scripts/test_k.sh` | 清理 → 重置 → 编译 → Agent → PX4/gz → DDS → 辅助节点 → 任务 |
| **③ 裁判** | `src/drone_drl/drone_drl/cuadc_judge.py` | 按规则计分 |

### 3.1 为什么要"生成"场地，而不是手写

**【经验/建议】** 这是本项目一个**很关键的设计**：

```
gen_world_cuadc.py --name k --seed 33
        │
        ├──► worlds/k.world         ← 给 Gazebo 看的
        └──► worlds/k.truth.json    ← 给检测器/裁判看的 (桶的真实坐标)
```

⇒ **桶的坐标只有一个来源** ✓ ⇒ 不会出现"改了一处忘了另一处" ✓
⇒ **换场地只需要换 `--seed`** ✓

> 💡 对比：我们的**复现对象**曾出现"裁判里桶坐标硬编码、而场地是随机生成"⇒ 判分完全错位 ✗。
> 我们用"同一次生成"从根本上杜绝了这类 bug ✓

### 3.2 真值从哪来【源码事实】

Gazebo Harmonic 的 **SceneBroadcaster** 会发布**所有模型的真实位姿**：

```
/world/<世界名>/dynamic_pose/info     (gz.msgs.Pose_V)   ← 真值!
```

我们用 `ros_gz_bridge` 把它转成 ROS 话题，再由 `impact_gt.py` 在**每次投放时**
记下飞机的**真值**位置 ⇒ 就能得到"**真值口径**"的分数 ✓（用 `GT_JUDGE=1 bash scripts/test_k.sh` 开启）

**踩过的坑**：`ros_gz_bridge` 把 `Pose_V → TFMessage` 时 **`child_frame_id` 全是空的** ✗
⇒ 不能按帧名找飞机 ⇒ 改成**按"索引 + 位置"锁定**（等某个实体真的出现在生成点附近才认）；
另外**第一帧到达时飞机还没被 spawn** ⇒ 必须先等 ✓

## 四、一步一步跑一轮

```bash
cd ~/SITL
colcon build --packages-select drone_drl
source install/setup.bash

bash scripts/test_k.sh          # ★ 跑一轮 (默认 Gazebo Harmonic)
```

**脚本会依次做**（【源码事实】）：
1. **清残留进程**（端口 11345/8888 + px4/gzserver/agent/ROS 节点）
2. **并发守卫**（有锁或残留 px4 就拒绝启动 —— 防止两个实例污染裁判）
3. **重置 PX4 持久化状态**（`dataman` / `parameters.bson` / `eeprom`）
4. **编译** `drone_drl`
5. 启动 **MicroXRCEAgent**（UDP 8888）
6. 启动 **PX4 SITL + Gazebo Harmonic**（轮询等待就绪）
7. 等 **DDS 话题**就绪
8. 启动**辅助节点**：检测器 + 裁判
9. 启动**任务节点** `k`
10. 结束后 `trap` 收尾（杀干净）

**产物**在 `runs/k_<seed>_<时间戳>/`：

| 文件 | 内容 |
|---|---|
| `mission.log` | **主日志**：状态机流转、`[K-ALIGN]`、`[K-SERVO]` 逐拍、`>>> DROP` 释放行 |
| `detector.log` | 检测器（`SIM bucket[...]` 是真值桶位，可用于核对）|
| `judge.log` | 裁判（每条规则判定）|
| `summary.json` | **分数**（`total_score` 应该是 800）|
| `world.sdf` / `truth.json` | 本轮场地的快照 |

**成功标志**：`summary.json` 里 `"total_score": 800` ✓

## 五、⚠️ 必写的坑

### 5.1 残留进程 —— 最高频的坑

**现象**：这一轮飞机**根本起不来**、0 投、一直挂到超时 ✗
**日志里**：`ERROR [px4] Task already running` + `gz_bridge failed to start and spawn model`

**原因**：上一轮（尤其是被 `Ctrl+C` 或超时杀掉的）留下了 `gz sim` / `px4` 进程，
新的 gz 起来后 PX4 以为"世界已经在运行" ⇒ 不去 spawn 飞机 ✗

**解决**：**每轮前清**

```bash
bash scripts/cleanup_sim.sh        # ★ 养成习惯
```

> 【经验/建议】更阴险的一种：**残留的 `ros_gz_bridge`** 会一直往 DDS 灌 250 Hz 的位姿数据，
> 把新的一轮的 OFFBOARD 流**饿死**（表现为解锁要 24 s、飞机飞到 39 m 高）✗
> 所以 `cleanup_sim.sh` **连 ROS 侧一起清** ✓

### 5.2 `pkill` 把自己杀了

**现象**：命令跑一半突然没了
**原因**：`pkill -f "xxx"` 会匹配**调用者自己的命令行**（如果里面含这个字符串）✗
**解决**：把清理写进**脚本文件**执行（脚本自己的 cmdline 不含那些模式串）✓

### 5.3 世界文件的三条规则

见上面 2.2 —— **别在世界里声明 gz system plugin**、**必须加 `<spherical_coordinates>`**、
**世界名要匹配** ✓

## 六、几个好用的开关

```bash
bash scripts/test_k.sh                    # 默认: 无界面 + EKF 口径
SIM_GUI=1   bash scripts/test_k.sh        # 打开 Gazebo 图形界面 (看飞机怎么飞)
GT_JUDGE=1  bash scripts/test_k.sh        # 真值口径打分 (额外起 pose 桥 + impact_gt)
bash scripts/test_k.sh hover_probe        # 悬停特性探针 (量"飞机能停多准")
SIM=classic bash scripts/test_k.sh        # 旧引擎 (本机没装, 会立刻报错)
```

**换场地**：

```bash
python3 scripts/gen_world_cuadc.py --name k7 --seed 7      # 生成新场地
WORLD_FILE=$PWD/worlds/k7.world TRUTH_FILE=$PWD/worlds/k7.truth.json \
GZ_WORLD=k7_gz bash scripts/test_k.sh                       # 用它跑
```

**跑分**：

```bash
bash scripts/bench_k_runs.sh 33 7 101     # 连跑多轮 (每轮自动清进程)
python3 scripts/bench_k_report.py          # 汇总所有轮次
```

## 七、动手练习

1. **跑一轮**，然后打开 `runs/k_33_*/mission.log`，找到 `>>> DROP #0!` 那一行，
   把它**每个字段**都解释一遍
2. **故意制造残留**：跑一轮 → `Ctrl+C` 打断 → 立刻再跑一轮 ⇒ 观察飞机起不来
   ⇒ 然后 `bash scripts/cleanup_sim.sh` 再跑 ⇒ 恢复正常 ✓
3. **换一个 seed** 生成场地，看 3 个桶的位置怎么变（`.truth.json` 是纯文本，直接看）
4. **开 `SIM_GUI=1`** 跑一轮，肉眼看看飞机在投放区上方是怎么挪的
5. **跑 `hover_probe`**，回答："这个仿真里，飞机定点悬停能停多准？"（结果会让你重新理解"精度"）
