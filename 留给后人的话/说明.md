## 一、最想让你先知道的五件事

### 1. 仿真分数不等于真实精度 —— 这是我们花最久才想明白的一件事

**【实测数据】**

| 口径 | 满分率 | A 区 | 单投中位 |
|---|---|---|---|
| EKF 口径（仿真默认裁判）| **10/11** | 21/22 | **3.34 cm** |
| 真值口径（Gazebo 真值）| **1/3** | 3/6 | **9.03 cm** |
| **释放残差**（环路真正在控的量）| — | — | **1.85 cm** |

**为什么差这么多**【源码事实】：仿真里检测器是**用 EKF 位置**造框的
（`px = 画面中心 + ((桶真值 − EKF位置)/高度)·fx`），而任务节点的反投影是它的逆运算
⇒ **整条视觉链测的是「EKF 眼里的桶偏移」，对 EKF 自身的绝对估计偏差「结构性失明」**；
而仿真的"落点"又恰好取 EKF 位置 ⇒ **EKF 偏差 1:1 变成"脱靶"**。

【实测数据】独立的真值对照显示，**PX4 SITL 的 EKF 有约 8 cm 的水平偏差（东向），且随飞行变化**。

**⇒ 你要记住的**：
- **别拿仿真分数当"我们的精度"对外报** ✗
- **仿真分数只用来判"链路是否正常"** ✓
- **要量精度，看「释放残差」**（实机上相机直接看桶 ⇒ 环路收敛真实相对几何）

📄 完整推导：[`../reports/k_accuracy_three_lenses_20261013.md`](../技术文档/专题报告/k_accuracy_three_lenses_20261013.md)

### 2. 实机上"飞机停不下来"才是最大的敌人，不是"瞄不准"

**【实测数据】** 2026-09-23 那趟两发都没中，但双链路对齐证明
**摄像头反投影是准的（corr 0.90/0.95）**，误差 100% 来自"飞机没停在桶上方"。

⇒ **调判据之前，先确认飞机能不能停稳**（看 ULog 的 vxy 和位置游走）。
如果飞机在 ±20 cm 游走，再准的判据也没用 ✗

---

### 3. 判据要"够得着"：宁可用可达的 5~10 cm + 必投，也别用够不到的 3 cm

- 3 cm 门限在实机摆动下**永远达不到** ⇒ 必然走兜底 ⇒ **释放时机变成随机的** ✗
- 好的设计是**三级**：好就早投（达标即投）→ 到释放面强制投 → 12 s 必投兜底
- **比赛的底线是"一定要投下去"** —— 0 分最差

---

### 4. 机械不对称，补偿就必须分开标定

**【实测数据】** 两瓶**镜像挂载**（第 1 瓶右、第 2 瓶左），早期给两瓶用了**同一个横向补偿**
⇒ 第 2 瓶方向反了 ⇒ "第 2 投总偏左"。
用实飞落点反推：第 1 瓶 **+9.8~+12.8 cm**，第 2 瓶 **−7.2~+2.3 cm（符号相反）**。

⇒ **别偷懒用一个常量覆盖两个不对称的东西。**

---

### 5. 换任何硬件（尤其相机）之后，所有标定值都作废

**【源码事实】** 2026-10-12 把相机换成 130° 原生画幅后，
**旧的投放补偿全部失效**（那是在旧相机模型下标定的）⇒ 我们把补偿**归零**
（`K_ZERO_COMPENSATION = True`），等实机重新标定。

⇒ **改硬件 ⇒ 重标定**，不要抱着旧值不放 ✗

## 二、踩过的坑（按"会浪费你多少时间"排序）

### 🔴 会浪费半天以上的

| 坑 | 现象 | 教训 |
|---|---|---|
| **残留仿真进程** | 下一轮 `Task already running` + `gz_bridge failed to start`，飞机**根本起不来**、0 投、挂到超时 | **每轮前 `bash scripts/cleanup_sim.sh`**；看到"飞机不起来"先怀疑残留 |
| **`SIM` 默认值没跟着迁移改** | `bash test_k.sh` 走进已卸载的 Gazebo Classic ⇒ **要等 600 s 轮询**才报错，看起来像"启动不了" | **迁移引擎/后端时，默认值要当场改掉** |
| **改了 `/etc/hosts`** | 里面有**工具管理的区块**（`# Steam++ Start/End`）—— 那是加速器的工作机制，不是屏蔽 | **改 hosts 前先看有没有 `# XXX Start/End`** |
| **`pkill -f` 写进交互式命令行** | **杀掉自己的 shell**（调用者 cmdline 含该模式串）| 清理一律放进**脚本文件**执行 |
| **他们（复现对象）的场地跑不起 PX4** | `Preflight Fail: ekf2 missing data` | 根因：**他们的世界没有任何碰撞体**（场地/起飞台都是 static + 0 collision）⇒ 飞机没地面 ⇒ 自由落体 ⇒ **补一个 `ground_plane`** |

### 🟠 会浪费几小时的

| 坑 | 现象 | 教训 |
|---|---|---|
| **gz 世界声明 system plugin** | `Found 0 compass` / `barometer missing` | gz 的 system plugin 由 `GZ_SIM_SERVER_CONFIG_PATH` **全局加载** ⇒ **世界里不要声明** |
| **gz 世界缺 `<spherical_coordinates>`** | `Preflight Fail: Strong magnetic interference` | 必加 |
| **世界文件名 ≠ `PX4_GZ_WORLD`** | `Timed out waiting for Gazebo world` | 名字必须一致 |
| **`ros-humble-ros-gz` 装错变体** | 与 Harmonic 不兼容 | 必须装 **`ros-humble-ros-gzharmonic`**（默认的是 Fortress 变体）|
| **实机订阅话题收不到数据** | 回调不触发 | 此固件话题名带 **`_v1`** 后缀 |
| **实机进不了 OFFBOARD** | offboard failsafe → AUTO_LAND | 节点必须在 PX4 **之前/同时**启动，持续发 setpoint >2 Hz |
| **YOLO 启动崩溃** | `_ARRAY_API not found` | 设 `PYTHONPATH` 指向 conda 环境的 site-packages |
| **摄像头分辨率不生效** | 设 640×480 还是 1920×1080 | 用 `cv2.CAP_V4L2` + MJPG fourcc |

### 🟡 认知类（不花时间，但会让你判断错）

| 坑 | 正确认知 |
|---|---|
| 用 `win=` 判"能否满足 3cm/2.0s" ✗ | **看 `触发方式=`** —— `win` 是"到达后已等待时长"（3.0 s 后容差放宽 +3 cm），不是稳定窗 |
| 用残差序列重建判据 ✗ | 日志节流 0.5 s，**释放快时一行都不打** ⇒ 会误判"样本 0 个 = 不满足"（实际那是最理想的情况）|
| 把"直径反推"里的 depth 改成斜距 ✗ | 必须与**检测器造框用的 depth 同模型**（我们的是垂直高度）；改斜距会让往返误差到 14 cm ⇒ **门把目标自己拒收** |
| 离线验收过了就以为能跑 ✗ | 有一次离线 104/104 全过，**真跑一轮却 `AttributeError`**（计数器在 DROP 入口初始化，但回调从起飞就跑）⇒ **改完必须跑一轮真仿真** |
| 用 SITL 分数评估实机精度 ✗ | 见第一节 |

## 三、如果重来一次，我们会怎么做【经验/建议】

1. **第一天就把"精度口径"定义清楚** —— 我们花了很久才意识到仿真分数不能当精度
2. **更早做"地板测量"** —— 用 `hover_probe` 先量出"这个仿真里飞机能停多准"，
   再决定判据该定多少（我们最后是这么做的，但做得有点晚）
3. **更早把日志分析自动化** —— 每次飞完手写复盘效率低，脚本化以后快得多
4. **一开始就把两瓶的补偿分开**（机械不对称是显然的，我们犯过）
5. **改动一律"一次一个变量 + 每步可回退"** —— 这条我们做得不错（生成器 + 锚点断言 + 自动备份），
   建议继续保持
6. **机械/硬件也留档案** —— 我们辛苦攒下的机械模型**只有一个 CATIA 文件集**，
   没有装配图、没有 STEP、没有实物照片 ⇒ 下一届很难接手 ✗

## 五、我们希望你保持的几条习惯

1. **每条结论都标来源** —— 这是本项目文档的基本约定：
   **【源码事实】/【实测数据】/【经验/建议】/【待验证】**
   ⇒ 别把"讨论过的方案"写成"已实现的功能" ✗
2. **不确定就说不确定** —— 标 `【待验证】`，别猜
3. **测量优先于推理** —— 这个项目里好几次"想当然"都错了，量一下才对
4. **每改一处，留证据** —— 离线验收（104 项 / 42 项）+ 至少跑一轮真仿真
5. **写下来** —— 你今天想明白的事，三个月后的你会忘，下一届更不会知道

## 六、最后

这个项目的技术难点其实不是"写代码"，而是**把"准不准"这件事量化清楚**：

- 一开始我们只知道"投不准"，但不知道不准在哪
- 后来学会了把误差拆成「**释放残差** ⊕ **桶估计误差**」
- 再后来发现**桶估计误差其实是仿真自己的问题**，不是我们的代码 ✗
- 最后才知道：**我们真正在控的那个量，中位只有 1.85 cm**

⇒ **"把误差拆开、给每一项找到证据"** —— 这是这个项目最值钱的方法论，比任何一行代码都值钱。
