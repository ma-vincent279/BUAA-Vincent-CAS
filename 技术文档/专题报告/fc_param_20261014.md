## 三、⚠️ 两个致命坑 (都实测踩过, 根因已定位)

### 坑 0 (前置): PX4 的 INT32 参数读回来是 float

`PARAM_VALUE.param_value` 是 float 字段, INT32 参数必须做**位重解释**。
不做的话 `EKF2_HGT_REF=1` 会读成 `1.4013e-45`。工具里已修:

```python
val = struct.unpack("<i", struct.pack("<f", msg.param_value))[0]
```

### 坑 1: 孤儿 NSH shell 会把 mavlink 线程卡死 ⇒ **只能拔插 USB**

**现象**: USB 设备还在 (`lsusb` 正常、内核无报错), 但串口 **0 字节**, 而且**写也阻塞**
(`serial.write` 挂住)。软件无法自救。

**根因**: PX4 只在收到 **`flags=0` (不要求响应) 的 SERIAL_CONTROL** 时才关闭 shell:

```cpp
// src/modules/mavlink/mavlink_receiver.cpp:2013
// if no response requested, assume the shell is no longer used
if ((serial_control_mavlink.flags & SERIAL_CONTROL_FLAG_RESPOND) == 0) {
    _mavlink.close_shell();
}
```

所以 shell 会话被 `kill` / `timeout` 掉 ⇒ FC 侧留下**孤儿会话**, 卡住 mavlink 收发。

**触发方式 (我犯的)**: 用 `timeout 60 python3 mavlink_shell.py /dev/ttyACM0` 跑命令 —— 超时被 kill。

**对策**:
- 批量/脚本一律用 **`fc_param.py nsh "<命令>"`** —— `try/finally + atexit + SIGTERM/SIGINT/SIGHUP`
  三层保证必发 close; 已实测「命令执行完遥测照常」✓
- 交互式才用 `mavlink_shell.py`, 退出用 **Ctrl-D**, **绝不套 `timeout`**
- 一旦卡死: **拔插 USB / 重新上电**, 没有别的办法

### 坑 2: `param select` 不带参数 ⇒ **空指针硬故障 ⇒ 复位**

**触发方式 (我犯的)**: 想查"参数存到哪", 跑了 `param select` (无参数)。飞控**当场复位**
(内核日志显示同一秒内 USB disconnect + 重新枚举, 产品串从 `PX4 CUAV 7 Nano` 变成 `PX4 BL CUAV 7 Nano`)。

**根因 (源码 + 飞控自己的 fault log 双证据)**:

```c
// src/lib/parameters/parameters.cpp:736
param_set_default_file(const char *filename)
{
    if ((param_backup_file && strcmp(filename, param_backup_file) == 0)) {   // filename == NULL 没人判空!
```

`param select` 无参数时走 `param_set_default_file(nullptr)` (`param.cpp:232`),
而本机 boot log 里 `param_backup_file` **非空** (`/fs/microsd/parameters_backup.bson`)
⇒ `strcmp(NULL, ...)` 读地址 0 ⇒ 精确数据总线错误 ⇒ Hard Fault ⇒ 复位。

**飞控自己写的 fault log 完全吻合** (`/fs/microsd/fault_2026_10_14_13_33_43.log`, 13:33:43 UTC = 本地 21:33:43):

```
Type:Hard Fault in file:armv7-m/arm_hardfault.c at line: 173 running task: param
r0:0x00000000 r1:0x38008840 ...        ← r0 = NULL(filename), r1 = 非空 backup file 指针
cfsr:0x00008200                        ← BFSR 0x82 = BFARVALID | PRECISERR (精确数据总线错误)
```

**影响面**: 复位后自愈; `param select` 的副作用**不持久** (boot log:
`INFO [param] selected parameter default file /fs/mtd_params`)、参数完好、无残留。
**⇒ 这就是 PX4 1.17 的一个真 bug, 值得上游报 issue。**

## 四、调参必须先知道的四条规矩

1. **`param set` 会自动落盘** —— `parameters.cpp:455` → `param_autosave()`
   (延时 ≥300 ms, 限流 2 s) ⇒ 值一变就写 flash, `+` 标记立刻置位。
   **没有"反悔窗口"**; 改前务必先 `dump` 备份。板上 `INFO [parameters] auto save: on` 已确认开启。
2. **只在未解锁时改** —— 源码注释写明写 flash 会让 CPU 停摆 ~300 ms (STM32F7/H7);
   PX4 在**解锁状态下会推迟落盘** (每秒重试)。工具已在 armed 时**直接拒绝**写与落盘。
3. **不要跑 `param select` / `param select-backup`** (坑 2)。
4. **`param show` 的行首标记是权威落盘状态**: `x`=used / `+`=saved / `*`=unsaved / `l`=locked
   —— 验证"到底存上没有"就靠它, 比任何间接推断都可靠。

## 五、工具用法 (`scripts/fc_param.py`)

```bash
python3 scripts/fc_param.py selftest                       # 5 步全链路自检 (只写同值)
python3 scripts/fc_param.py info                           # 板子信息 + 参数表 + 首飞清单参数

python3 scripts/fc_param.py save                           # 单独落盘
python3 scripts/fc_param.py dump 备份.txt                  # 备份全部参数
python3 scripts/fc_param.py diff 备份.txt                  # 对比改了哪些
python3 scripts/fc_param.py restore 备份.txt [--yes]       # 按备份还原 (默认只演练)
```


### D. ⚠️ 解读口径 (别踩的坑)

1. **不是所有"差异"都是用户设置**: 手上是 `CUAV_7_NANO`、真机是 `PX4_FMU_V6C`,
   两者的 **board defaults 本来就不同** (如 `COM_CPU_MAX` / `RC_CHAN_CNT` / `PWM_MAIN_*` 之类)。
   ⇒ 换机时**不要照抄板级默认值**, 只抄 C 节那类**有意设置**。
2. **画像里的 `CAL_*` 是"该机最后一次标定值"**: 换机/重标后必然不同, **绝对不能抄**。
3. **画像只用于"比对", 不要用来"整机回灌"**: `restore` 是逐项 `PARAM_SET`,
   对 1160 项做整机写入既慢又险; 正确用法是 `diff` 出差异后**只改该改的那几项**。
